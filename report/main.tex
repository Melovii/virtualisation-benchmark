\section{Introduction}
\label{sec:introduction}
% DRAFT. Rewrite in your own words: the guidelines require that motivation and question are yours.
Organizations running web services in the cloud must decide whether to package an application as a virtual machine (VM) image or as a container image. Both isolate the application, but a VM carries its own operating-system kernel while a container shares the host kernel. In practice this should affect how quickly new capacity becomes available, how much memory and disk each instance consumes, and possibly request latency. These properties matter for autoscaling, density, and cost.

\textbf{Question.} On one host, with the same application, the same Ubuntu 24.04 user space, and the same budget of two CPU cores and 2~GB of memory, (a) how much faster does a Docker container become ready than a QEMU/KVM VM, (b) how much memory and disk does each use, and (c) do steady-state throughput and response time differ?

\textbf{Approach.} We run one small Flask API two ways: in a QEMU/KVM VM and in a Docker container built on the same Ubuntu 24.04 user space. We measure each alternative at least three times with an automated harness. Section~\ref{sec:related_work} gives background, Section~\ref{sec:design} the design, Section~\ref{sec:methodology} the method, Section~\ref{sec:results} the results, and Sections~\ref{sec:discussion} and~\ref{sec:conclusion} the discussion and conclusion.

\section{Background and Related Work}
\label{sec:related_work}
% DRAFT. Read every cited source before keeping its sentence. Write the synthesis yourself.
\textbf{Service models and virtualization.} The NIST definition~\cite{b1} and the course textbook~\cite{b2} describe virtual machines as the basis of infrastructure as a service. A hypervisor presents virtual hardware to a guest operating system, which boots its own kernel. With KVM the Linux kernel itself acts as the hypervisor and runs guest code directly on the CPU with hardware support, while QEMU emulates the virtual devices in user space. On Windows, WSL2 itself runs inside a lightweight virtual machine, so a KVM guest started in WSL2 is a nested virtual machine.

\textbf{Containers.} On Linux, containers are ordinary processes isolated with kernel namespaces and limited with control groups (cgroups); all containers share the host kernel. Docker exposes these limits through options such as \texttt{--memory} and \texttt{--cpuset-cpus}~\cite{b4}, which we use to give containers the same budget as the VM.

\textbf{Related work.} Felter et al.~\cite{b3} compared native Linux, KVM, and Docker for CPU, memory, network, and disk workloads and reported low overhead for both virtualization styles, with network address translation as a notable cost. \todo{After reading the paper: state in one or two sentences what it did NOT measure that you measure (for example, time to become ready), and how your setup differs (a Flask API instead of Redis and MySQL, WSL2 and therefore a nested guest).}

\textbf{Tools.} We run the VM with QEMU/KVM~\cite{b5} and generate load with ApacheBench (\texttt{ab})~\cite{b6}, which sends a fixed number of requests with a fixed number of concurrent connections.

\subsection{Architecture}
Fig.~\ref{fig:architecture} shows the setup. Everything runs inside one WSL2 Linux instance. The load generator (\texttt{ab}) is pinned to cores that the system under test does not use. It sends HTTP requests either to the VM over a TAP network (192.168.100.2:5000) or to the container on Docker's bridge network (its bridge IP, port 5000); neither path uses address translation. Only one target runs at a time. In every case the same gunicorn server with two workers serves the same Flask application with three endpoints.

\subsection{Measurements}
\textbf{Time to ready (s):} wall-clock time from immediately before the start command (\texttt{qemu-system-x86\_64} or \texttt{docker run}) until the first HTTP 200 from \texttt{/health}, polled every 20~ms. One discarded warm-up round precedes three measured rounds in random order. \textbf{Memory (MB):} sampled 20~s after readiness and during load. For the VM we report the host-side resident size of the QEMU process and the memory used inside the guest; for containers, the cgroup memory counter shown by \texttt{docker stats}. \textbf{Disk (MB):} space allocated by the VM's qcow2 image file and the image size reported by Docker for containers. \textbf{Throughput (req/s) and latency (ms):} ApacheBench with 50 concurrent connections and 20000 requests per measurement, on two workloads: \texttt{/compute} (CPU-bound, 5000 chained hashes) and \texttt{/} (a tiny response, dominated by the network and server stack). Keep-alive is off, so each request opens a new connection. \textbf{Cost (USD):} all resources are local, so the cost is zero apart from electricity, which we do not measure.
